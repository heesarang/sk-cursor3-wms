## 1. 배경 및 목적

### 1.1 운영 요청 (원문)

> (물류센터 운영) 입고 오더마다 거래처 담당자 연락처를 화면에서 바로 보고 싶습니다.  
> 지금은 전화번호를 다른 데 적어 두고 찾느라 시간이 걸립니다.  
> 입고 목록·상세에 담당자 연락처를 넣어 주세요.

### 1.2 As-Is

| 영역 | 현재 | 문제 |
|------|------|------|
| 데이터 | `inbound_order`에 담당자 연락처 컬럼 없음 | 주문과 연락처가 시스템에 연결되지 않음 |
| 화면 | 입고 목록·상세에 연락처 미표시 | 별도 메모·엑셀을 찾아 통화에 시간 소요 |
| API | 목록·상세 응답에 연락처 필드 없음 | 화면에서 표시할 소스 없음 |

### 1.3 To-Be

입고 주문(오더) 단위로 **거래처 담당자 연락처**를 보관하고, **입고 목록·상세 화면에서 바로 확인**할 수 있게 한다.

운영자는 검수·확정 업무 중 거래처에 문의할 때 화면을 떠나지 않고 연락처를 볼 수 있어야 한다.

### 1.4 범위

| 포함 | 제외 |
|------|------|
| 입고 주문(`inbound_order`)에 연락처 컬럼 추가 | 거래처(파트너) 마스터 테이블·CRUD 화면 |
| 입고 목록·상세 API 응답에 연락처 포함 | 출고 주문 연락처 (본 요청 범위 외) |
| 입고 목록·상세 UI에 연락처 표시 | 연락처 수정 전용 API·화면 (초기값은 시드/마이그레이션·후속 확장) |
| 마이그레이션 + 기준 DDL·데이터 사전 동기화 | 인증·권한 변경, F5~F7 재고 흐름 |

기본 PRD F1~F4로 이미 만든 REQ·UI·Task 문서는 **새 변경용 산출물로 갱신**하거나 영향 목록에 따라 최소 수정한다. 기준 DDL은 **직접 재작성만 하지 말고** `database/migrations/`에 ALTER를 남긴 뒤 기준 DDL·사전을 맞춘다 (`10-change-request.md`).

## 2. 기능 요구사항

### CR-F1-01. 입고 주문에 담당자 연락처 보관

- 입고 주문 헤더에 거래처 담당자 연락처를 저장할 수 있어야 한다.
- 기존 주문에는 값이 없을 수 있으므로 **NULL 허용**이다. (필수화는 데이터 정비 후 별도 변경)

### CR-F1-02. 입고 목록에서 연락처 표시

- 입고 주문 목록에서 각 행의 담당자 연락처를 확인할 수 있어야 한다.
- 값이 없으면 빈 값 또는 `-` 등 부재 표시로 충분하다.

### CR-F1-03. 입고 상세에서 연락처 표시

- 입고 주문 상세(다이얼로그/상세 영역)에서 담당자 연락처를 확인할 수 있어야 한다.

### CR-F1-04. 기존 입고 기능 회귀 유지

- 센터·상태 필터, 목록·상세 조회, 상태 전이(검수시작 → 검수완료 → 입고확정)는 기존과 동일하게 동작해야 한다.
- 대시보드·출고 기능은 본 변경으로 깨지지 않아야 한다.

## 3. 데이터 요구사항

물리 컬럼명은 설계자가 `06-database.mdc`에 맞춰 정한다. 아래는 **예시(권장)**이다.

| 항목 | 값 |
|------|------|
| 대상 테이블 | `wms.inbound_order` |
| 컬럼(예시) | `partner_contact_tel` |
| 타입 | `VARCHAR(20)` |
| NULL | 허용 (`NULL`) |
| 기본값 | 없음 |
| COMMENT(예시) | `거래처 담당자 연락처 (예: 010-1234-5678)` |
| 위치 | **공통 감사 컬럼(`created_at` 등) 뒤**에 추가 (`ALTER` 물리 순서와 기준 DDL 일치) |

**비고**

- 거래처 마스터를 신설하지 않는다. 연락처는 입고 주문에 **비정규화(스냅샷) 속성**으로 둔다.
- 화면에서 신규 입력·수정이 당장 필수는 아니다. 조회 표시가 Must이며, 시드/마이그레이션 샘플 값으로 확인 가능하면 충분하다.
- 이름 후보가 달라도 표준(두 단어 이상 snake_case, 약어 접미어 금지)만 지키면 된다.

## 4. API·화면 영향 (초안)

| 구분 | 영향 |
|------|------|
| API | `GET /api/inbound/orders`, `GET /api/inbound/orders/{orderNo}` 성공 응답에 연락처 필드 추가 (snake_case) |
| 전이 API | Body·전이 로직 변경 없음 (조회 필드만 확장) |
| UI | 입고 목록 테이블 컬럼, 입고 상세 헤더 영역에 연락처 표시 |
| Mapper/XML | 입고 목록·상세 SELECT에 컬럼 포함 |
| DB | `migrations/YYYYMMDD_NNN_add_*_to_inbound_order.sql` + `wms_ddl.sql` + `data-dictionary.md` |

상세 Method/Path/응답 JSON은 후속 요구사항 정의서(REQ) 또는 기존 `REQ-F1-inbound.md` §5 갱신에서 확정한다.

## 5. 비기능·제약

| 구분 | 요구 |
|------|------|
| 변경 관리 | DB 직접 ALTER 금지. 마이그레이션 파일 작성 후 승인·적용 |
| 표준 | `std_check` PASS 유지 (COMMENT·명명·타입) |
| 호환 | 기존 시드·주문 행이 있어도 마이그레이션이 실패하지 않을 것 (NULL 허용) |
| 보안 | 연락처는 개인정보에 가깝다. 본 실습에서는 인증 없이 조회하되, 실계정·비밀번호는 Git에 올리지 않는다 |

## 6. 인수 기준 (Acceptance)

1. DB: `inbound_order`에 연락처 컬럼이 있고 COMMENT가 있다.
2. API: 입고 목록·상세 JSON에 연락처 필드가 포함된다 (값 또는 null).
3. UI: 입고 목록·상세에서 연락처를 확인할 수 있다.
4. 회귀: 입고 상태 전이·대시보드 조회가 기존과 같이 동작한다.
5. 산출물: 마이그레이션 파일 + 기준 DDL + 데이터 사전이 서로 맞다.
