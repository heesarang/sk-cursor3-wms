# 10. Change Request — 운영 변경 대응 (컬럼 추가)

> 2일차 ③ 꼭지(1.5h). 앞 꼭지에서 만든 F1 입고 기능에 운영 변경 요청 1건을 실무 절차대로 반영한다. 모델은 전 단계 Composer 2.5.

## 1. 변경 요청

> "입고 오더에 거래처 담당자 연락처를 기록해야 합니다. 목록과 상세에서 보이게 해 주세요."

운영 요청 중 가장 흔한 유형(기능 개선, DB 변경이 화면까지 미침)이다. 정답 diff는 없다. 수강생마다 앞 꼭지 코드가 다르기 때문이다. 아래 절차와 확인 포인트로 평가한다.

## 2. 절차 6단계

| 단계 | 할 일 | AI에게 시키는 것 | 사람이 확인하는 것 |
|---|---|---|---|
| 1. 접수 | 요청을 한 문장 명세로 바꾼다 | "이 요청의 입력·출력·제약을 정리해줘" | 컬럼 의미, 필수 여부, 길이 |
| 2. 영향 파악 | 바뀌는 파일 목록을 먼저 만든다 | "@wms_ddl.sql 기준으로 이 컬럼 추가가 영향을 주는 테이블·DTO·Mapper·API·화면 파일을 목록으로" | 목록을 저장해 두고 6단계에서 실제 수정 파일과 비교 |
| 3. 마이그레이션 | `database/migrations/20261029_001_add_contact_tel_to_inbound_order.sql` 작성 | 06-database Rule이 자동으로 붙는다 | `ALTER TABLE ... ADD COLUMN` + `COMMENT ON COLUMN`, 직접 DB 실행 금지 |
| 4. 기준 DDL 동기화 | `database/schemas/wms_ddl.sql`에 같은 컬럼을 **공통 컬럼 뒤에** 추가, 데이터 사전 갱신 | "마이그레이션과 기준 DDL이 같은지 비교해줘" | `std_check` PASS |
| 5. 백엔드·화면 반영 | DTO, Mapper(XML), API 응답, 목록·상세 화면 | 2단계 목록대로 한 파일씩 | 다른 기능 파일을 건드리지 않았는가 |
| 6. 검증 | 시드 조회, 상태 전이 회귀 | "기존 상태 전이 테스트를 다시 돌려줘" | 2단계 목록과 실제 수정 파일 비교 |

## 3. 컬럼 정의 (예시)

| 항목 | 값 |
|---|---|
| 컬럼 | `partner_contact_tel VARCHAR(20) NULL` |
| 코멘트 | `'거래처 담당자 연락처 (예: 010-1234-5678)'` |
| 이유 | 기존 오더에는 값이 없으므로 NULL 허용. 필수화는 데이터 정비 후 별도 변경으로 |

이름은 표준(두 단어 이상, snake_case, 약어 접미어 금지)만 지키면 수강생이 정해도 된다.

## 4. 확인 포인트

- DB에 직접 ALTER 하지 않고 `migrations/20261029_001_*.sql`로 남겼는가
- 기준 DDL `wms_ddl.sql`에도 같은 컬럼이 공통 컬럼 뒤에 추가됐는가
- `std_check` PASS 유지 (COMMENT, 길이, 명명)
- 기존 기능(상태 전이, 대시보드)이 그대로 동작하는가
- 2단계 영향 목록과 실제 수정 파일이 얼마나 일치했는가 (AI 영향 파악의 정확도)

## 5. 자주 나오는 실수

| 실수 | 결과 | 막는 방법 |
|---|---|---|
| DB에 바로 ALTER | 기준 DDL·이력과 실제 DB가 어긋남 | 06-database Rule §9, 리뷰 |
| 기준 DDL에서 컬럼을 중간에 끼움 | 실제 물리 순서와 달라짐 | 공통 컬럼 뒤에 추가 |
| COMMENT 누락 | std_check 실패, 다음 AI가 의미를 모름 | std_check |
| 화면만 고치고 Mapper 누락 | 값이 저장되지 않음 | 2단계 목록 대조 |
