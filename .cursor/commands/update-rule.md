# 규칙 수정/추가 커맨드

> 출처: mySUNI AI Coding 운영 자산(2026-01)의 `/update-rule`을 WMS 저장소 Rule 목록에 맞춰 조정. 수정안은 `00-rule-authoring.mdc` 기준을 따른다.

## 작업 지시

현재 세션의 대화 내용을 분석하여 다음을 수행하세요:

### 1단계: 세션 분석

현재 세션에서 다음 사항을 파악합니다:
- **문제점**: 사용자가 불만족한 결과물이 무엇인가?
- **원인 규칙**: 어떤 규칙이 해당 결과물을 유발했는가?
- **개선 방향**: 어떻게 규칙을 수정해야 더 나은 결과가 나오는가?

### 2단계: 규칙 파일 확인

`.cursor/rules/` 디렉토리에서 관련 규칙 파일을 찾습니다:
- 00-rule-authoring.mdc (Rule 작성 기준)
- 01-project-context.mdc
- 02-java-backend.mdc
- 03-mybatis-mapper.mdc
- 04-frontend.mdc
- 05-status-transition.mdc
- 06-database.mdc

### 3단계: 수정 제안

사용자에게 다음 형식으로 수정 제안을 합니다:

```
## 분석 결과

**문제점**: [세션에서 발견한 문제 설명]

**관련 규칙**: [수정이 필요한 규칙 파일명]

**현재 규칙**:
[현재 규칙 내용]

**수정 제안**:
[수정된 규칙 내용]

**수정 이유**:
[왜 이렇게 수정하면 더 나은 결과가 나오는지 설명]
```

### 4단계: 사용자 확인 후 적용

사용자가 수정 제안을 승인하면:
1. 해당 규칙 파일을 수정합니다
2. 규칙 작성 가이드라인(rule-authoring-guidelines.mdc)을 준수합니다
3. 수정된 내용을 요약해서 보여줍니다

새 규칙이 필요한 경우:
1. 적절한 파일명(kebab-case)으로 새 규칙 파일을 생성합니다
2. 규칙 템플릿 구조를 따릅니다

## 규칙 구조 템플릿

```markdown
---
description: "[한 문장으로 규칙의 목적 설명]"
alwaysApply: [true|false]
[globs: ["**/*.ts", "**/*.tsx"]] # 선택사항
---

# [규칙 제목]

[규칙의 배경 및 목적 설명]

## [섹션 제목]

**Rule:** [명확하고 실행 가능한 규칙 문장]

**Reasoning:**
- [규칙이 존재하는 이유]
- [해결하는 문제]

#### Recommended Pattern:

[올바른 접근 방법의 코드 예제]

#### Anti-Pattern:

[피해야 할 접근 방법의 코드 예제]
```

## 규칙 작성 원칙

- **명확한 언어**: "MUST", "SHOULD", "MUST NOT" 사용
- **모호한 표현 금지**: "가능하면", "적절하게" 사용 금지
- **예제 필수**: Recommended Pattern과 Anti-Pattern 모두 포함
- **500줄 제한**: 초과 시 여러 규칙으로 분리
- **중복 방지**: 기존 규칙과 충돌하지 않도록 확인

## 규칙 작성 체크리스트

수정/추가 전 다음 사항을 확인합니다:

- [ ] **목표가 한 문장으로 명확히 정의됨**
- [ ] **범위가 구체적임** (globs/작업 타입이 명확함)
- [ ] **가이드라인이 검증 가능함** (모호한 표현 없음)
- [ ] **예제/참조가 포함됨** (Recommended Pattern과 Anti-Pattern 모두)
- [ ] **다른 규칙과 중복/충돌 없음**
- [ ] **적용 방법이 적절함** (Always/Intelligent/Specific/Manual)
- [ ] **500줄 이하** (초과 시 여러 규칙으로 분리)

## 메타데이터 설정 가이드

### alwaysApply 결정
- `true`: 모든 채팅 세션에서 항상 적용 (예: 코딩 표준, 아키텍처 원칙)
- `false`: 특정 컨텍스트에서만 적용 (description과 globs로 제어)

### globs 설정 (선택사항)
- 특정 파일 타입에만 적용: `["**/*.tsx", "**/components/**"]`
- 전체 프로젝트: 생략 또는 `["**/*.ts", "**/*.tsx"]`

## 주의사항

1. **규칙 우선순위**: Team → Project → User 순서로 적용
2. **규칙 길이**: 500줄을 초과하면 여러 규칙으로 분리
3. **중복 방지**: 기존 규칙과 중복되지 않도록 확인
4. **검증 가능성**: 모호한 표현 대신 검증 가능한 기준 사용
5. **예제의 중요성**: 모든 규칙은 즉시 적용 가능한 예제 포함
